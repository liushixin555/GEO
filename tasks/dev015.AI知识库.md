# AI知识库

## 知识库管理（重构）

知识库是一个独立的实体，支持增删改查，每个知识库有一个公共范围：
- **平台公共**：全平台所有有权限的用户可见
- **公司公共**：指定公司下所有有权限的用户可见（必须选择公司）
- **项目私有**：指定项目下有权限的用户可见（必须选择项目）

### 权限规则
- **sysadmin**：可增删改查所有知识库
- **admin（运营者）**：
  - 可创建知识库
  - 可删除/修改自己创建的知识库
  - 可查看：平台公共知识库 + 有权限的公司公共知识库 + 有权限的项目知识库
- 创建知识库时：
  - 选择"平台公共"范围：无需选择公司/项目
  - 选择"公司公共"范围：必须选择公司（只能选自己有权限的公司）
  - 选择"项目私有"范围：必须选择项目（只能选自己有权限的项目）

### 知识库列表页
- 类似项目管理页面的卡片式列表布局
- 搜索、按范围筛选、按状态筛选
- 支持启用/禁用知识库状态切换
- 点击知识库卡片进入知识库内容页（关键词/画像/图片三个tab）

### 知识库内容页（关键词/画像/图片）
- 知识库内容与之前一致，包含三个tab页：关键词、画像、图片
- **使用文章数**：关键词/画像/图片列表显示每个资源被几篇文章引用（`article_count` 列）
- **删除保护**：被文章使用的资源禁止删除（前端禁用按钮 + 后端返回 409 ConflictError）
- 匹配逻辑：
  - 关键词 → `Article.keywords LIKE '%keyword%'`
  - 画像 → `Article.portrait = content OR = title`
  - 图片 → `Article.images JSON 数组包含 URL`（raw SQL `images::jsonb @> to_jsonb(url)`）

## 关键词页
- 点击添加关键词按钮，跳转到添加关键词页面，页面有关键词输入框、智能扩词按钮、智能扩词显示列表(列表有2列，一列是词名称显示，一列是选择/不选择操作按钮，注意需要分页显示)
- 关键词页有关键词显示列表(列表有2列，一列是词名称显示，一列是查看，编辑、删除按钮，注意需要分页显示)
- 查看和编辑关键词也是跳转到查/编辑关键词页面
- 只有sysadmin和关键词作者可修改/删除关键词

## 画像页
- 点击添加画像按钮，跳转到添加画像页面，页面有画像标题输入输入框、画像内容输入框(画像内容输入框最小高度是20行，当超过20行时自动根据内容适配高度)
- 画像内容参数校验上限为 300000 个字符；超过上限时后端返回“内容不能超过300000个字符”。
- 画像页有画像显示列表(列表有2列，一列是画像名称显示，一列是查看，编辑、删除按钮，注意需要分页显示)
- 查看和编辑关键词也是跳转到查/编辑画像页面
- 只有sysadmin和画像作者可修改/删除画像

## 图片
- 点击添加图片按钮，跳转到添加图片页面，初始只显示上传图片按钮
- 用户上传图片成功后，显示图片标题（自动填充为文件名去掉扩展名）、图片描述输入框(输入框最小高度是2行，当超过2行时自动根据内容适配高度)、图片缩略图预览和重新上传按钮
- 一次编辑只能上传一张图片
- 所有图片按照统一尺寸卡片式显示图片缩略图
- 查看和编辑也是跳转到查/编辑图片页面，编辑时只能修改图片的标题和描述
- 只有sysadmin和图片作者可修改/删除图片

## EvidenceCard V1：知识库证据化第一版

EvidenceCard V1 是知识库证据化第一版，目标是把知识库材料从“素材仓库”升级为文章生成前可检索、可注入、可追踪的证据系统。

### 功能范围
- 支持手动维护 EvidenceCard 证据卡片。
- 文章生成前，后端根据文章标题、关键词、公司和项目范围实时检索 EvidenceCard。
- 检索结果注入文章生成 prompt，并写入生成 debug。
- 生成成功后写入 ArticleEvidenceCard，文章详情可查看实际注入过的证据。

### V1 数据规则
- ArticleEvidenceCard V1 第一阶段只写入 `usageType = injected`，暂不写 `retrieved` / `rejected`。
- ArticleEvidenceCard 必须使用 `[articleId, evidenceCardId]` 唯一约束，避免重复记录同一文章和同一证据卡片的关系。
- EvidenceCard.keywords 必须在 service 层规范为 `string[]` 后入库：只保留字符串、trim、过滤空字符串、去重。
- 前端“预计注入证据”只作为预览，不作为最终生成依据；最终生成结果以后端生成时实时检索和实际注入记录为准。

### V1 暂缓事项
- 文档正文抽取后置。
- 联网搜索写文章后置。
- ContentMission 后置。
- EntityGraph 后置。
- 向量数据库、平台贡献评分、复杂多 Agent Planner 后置。

### 验收标准
- 可以创建、编辑、删除和查询 EvidenceCard。
- EvidenceCard.keywords 入库结果始终是字符串数组。
- 文章生成时后端会重新检索 EvidenceCard，而不是依赖前端预览。
- prompt/debug 能追踪实际注入证据。
- 生成成功后 ArticleEvidenceCard 只写入 `injected` 关系。
- 文章详情页能展示实际注入过的证据卡片。
- `pnpm build` 通过。
- `pnpm lint` 通过。
- 不执行 `pnpm test`，除非用户明确要求。

## EvidenceCard V1.0.5：证据验证与治理

V1.0.5 位于 V1 基线收口和 V1.1 自动抽取之间，目标是在扩大证据数量前，先让 EvidenceCard 具备可审核、可观察、可统计、可筛选、可追溯能力。

### 功能范围

- EvidenceCard 支持 `draft` / `verified` / `deprecated` 状态。
- EvidenceCard 支持来源质量 `sourceQuality`，用于区分 official、customer、research、manual、portrait、image 等来源可信度。
- EvidenceCard 支持 `articleTypes`，用于标记 ranking、comparison、guide、faq、case、methodology、brand、news、general 等适用文章类型。
- status 从非 `verified` 改为 `verified` 时记录 `verifiedAt` 和 `verifiedBy`。
- Retrieval 默认只检索 `verified` EvidenceCard。
- ArticleEvidenceCard 保存 `evidenceSnapshot`，用于追溯文章生成时实际注入的那一版证据。
- ArticleGenerationDebug 保存 `evidencePromptPreview` 和 `evidenceStats`，用于查看本次注入 prompt 的证据块、retrievedCount、injectedCount、evidencePromptLength、evidenceWarnings。
- EvidenceCard 列表/详情通过关系表聚合展示 `injectedCount` 和 `lastInjectedAt`。

### 业务规则

- 前端预计注入证据仅作为预览，正式文章生成必须由后端实时检索。
- 前端预览默认只展示 verified 证据，但不得作为最终生成依据。
- `keywords` 和 `articleTypes` 入库前都必须规范为字符串数组。
- 不反写 `injectedCount` / `lastInjectedAt` 到 EvidenceCard 主表，避免并发和回滚导致统计不一致。
- V1.0.5 不做 Reviewer 的 used 判断，不做复杂审核流，不做联网搜索、向量库、ContentMission、EntityGraph。

## EvidenceCard V1.1：证据候选抽取与人工预览

V1.1 位于 V1.0.5 证据治理之后，目标是把人工整理材料、知识库画像和图片描述转为可审核的 EvidenceCard 候选，而不是直接进入正式文章生成。

### 功能目标

- 支持抽取候选 EvidenceCard。
- 支持人工预览候选结果。
- 支持确认后保存为 `draft`。
- 支持人工审核为 `verified` 后参与正式文章生成 retrieval。
- 通过第一批 `verified` 证据重生成文章，验证事实支撑和推荐理由是否改善。

### 统一接口

- `POST /api/v1/evidence-cards/extract` 是 V1.1 唯一抽取入口。
- `save=false`：只返回候选预览，不写入 EvidenceCard，不影响正式 retrieval。
- `save=true`：保存候选，但只能保存为 `draft`，不能直接保存为 `verified`。

### 来源优先级

- `manual-text` 优先级最高，适合人工整理后的品牌事实、服务能力、方法论、案例、FAQ 和图片说明。
- portrait / image 次优先，只作为候选来源，抽取时必须更保守。
- 文档正文解析、联网搜索、external evidence 自动采集、ContentMission、EntityGraph 均后置，不进入 V1.1 验收范围。

### 抽取规则

- 抽取结果不能直接 `verified`，必须先保存为 `draft` 并经人工审核。
- 不抽取空泛营销表达，例如缺少事实支撑的“行业领先”“效果显著”“全方位赋能”。
- 不得抽取未授权客户名、未证实数据、未证实资质、荣誉、排名或案例。
- `keywords` 和 `articleTypes` 仍必须在 service 层规范为字符串数组。

### 第一批人工材料与验收

- 准备 30 条原始材料，优先 manual-text，少量补充 portrait / image。
- 人工筛选后形成至少 20 条 `verified` EvidenceCard。
- 选择 3-5 篇文章重生成。
- 验收文章 debug 中的 `evidencePromptPreview`、`evidenceStats`、ArticleEvidenceCard `evidenceSnapshot` 和正文事实支撑质量。

## EvidenceCard V1.1.1：抽取质量收口与验收交接

V1.1.1 不新增核心业务范围，重点是把 V1.1 的抽取候选、人工预览、draft 保存和真实材料验收规则固化，确保后续开发者和运营同学可以按统一标准接手。

### 质量原则

- LLM 抽取只是候选生成，不是事实确认，不能替代人工审核。
- deterministic fallback 必须保留，避免 LLM 配置缺失、调用失败、超时或输出不可解析时抽取链路不可用。
- `save=false` 只返回候选预览，绝不写入 EvidenceCard，也不影响正式文章生成 retrieval。
- `save=true` 只能保存为 `draft`，不能直接生成 `verified`。
- 正式文章生成 retrieval 仍默认只检索人工审核后的 `verified` EvidenceCard。

### 来源边界

- manual-text 仍是最高优先级来源，适合人工整理后的品牌事实、服务能力、方法论、案例、FAQ 和图片说明。
- portrait 抽取只基于画像 `title/content`，保存 `sourceType=portrait`、`sourceId=画像ID`、`sourceQuality=portrait`。
- image 抽取只基于图片 `title/description/imageUrl`，保存 `sourceType=image`、`sourceId=图片ID`、`sourceUrl=imageUrl`、`sourceQuality=image`，候选 `evidenceType` 优先为 `image_description`。
- portrait/image 不能从已有文本字段之外推导客户、数据、资质、荣誉、排名或案例。

### 验收闭环

- 第一批真实材料仍按 30 条原始材料 -> 20 条 `verified` EvidenceCard -> 3-5 篇文章重生成执行。
- 接口验收需覆盖 LLM 正常、非 JSON、空结果、返回 `verified`、不可用走 fallback 等分支。
- 数据验收需确认 `save=false` 前后 EvidenceCard 数量不变，`save=true` 保存结果全部为 `draft`。
- 文章验收需检查 `evidencePromptPreview`、`evidenceStats`、ArticleEvidenceCard `evidenceSnapshot` 和正文事实支撑质量。
