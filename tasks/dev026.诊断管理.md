# dev026. 诊断管理（AI 可见度诊断）

> 状态：✅ 已完成

---

## 功能说明

替代原 `geo-audit` Redis KV 实现，提供对目标品牌在多个 AI 引擎（豆包 / DeepSeek / 通义 / 元宝 / 文心一言）中的「AI 可见度诊断」能力。一次诊断会按品牌 / 品类 / 竞品 / 购买意图 / 对话型 / 发现型 6 个维度批量投递中文提示词，对每个引擎的回复做提及 / 情感 / 盲点分析，最终聚合出 0-100 分、A+~F 等级、改进建议与可下载的诊断 Skill ZIP。

### 命名约定（铁律）

- **代码层**：保留英文 `audit`（`Audit` 模型、`/api/v1/audit`、`AuditService`、`apis/audit/`、`pages/audit/`）
- **用户可见中文**：统一称为「诊断」——菜单「诊断管理」、按钮「新建诊断」、详情「诊断报告」
- 旧的「审计日志」（audit-log）模块的用户可见文案也同步改为「诊断日志」，但路由 / 模型代码不变

## 数据模型

新增 3 张表（`prisma/migrations/20260628000000_add_audit/migration.sql`）：

- **`audits`** — 一次诊断任务（jobId / brand / status / score / grade / result 快照 / 4 个子检查 JSON / 引擎数 / 提示词进度）
- **`audit_prompts`** — 每条提示词 × 引擎的执行单元（`[auditId, promptIndex, engine]` 唯一）
- **`audit_prompt_results`** — 单次引擎调用的回复分析（mentioned / snippet / sentiment / blindSpot / latencyMs / error）

详见 [db.数据模型变更汇总.md](./db.数据模型变更汇总.md) 的 db024 条目。

## API

挂载点：`app.use('/api/v1/audit', authMiddleware, roleMiddleware(SYSADMIN, ADMIN))`（antiCrawl / rateLimit 已在全局应用）。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET  | `/api/v1/audit` | 当前用户可见的诊断列表（sysadmin 看全部，admin 仅看自己） |
| GET  | `/api/v1/audit/:jobId` | 诊断详情（含 result + prompts） |
| DELETE | `/api/v1/audit/:jobId` | 软删除 |
| GET  | `/api/v1/audit/:jobId/status` | 执行状态（promptDone / promptTotal） |
| POST | `/api/v1/audit/detect` | 品牌自动检测（URL → brand / website / industry 推断） |
| POST | `/api/v1/audit` | 创建诊断任务（同步生成提示词计划） |
| POST | `/api/v1/audit/:jobId/execute` | 触发批量异步执行 |
| POST | `/api/v1/audit/:jobId/rerun` | 重新诊断（基于原配置创建新任务并自动执行） |
| GET  | `/api/v1/audit/:jobId/skill` | 下载诊断 Skill ZIP（Buffer） |

> 路由顺序铁律：固定路径（`detect`）必须在 `:jobId` 之前，否则会被解析为 jobId。

## 业务规则

1. **权限**：仅 sysadmin / admin 可访问；view 角色完全无权限。sysadmin 看所有诊断，admin 仅看自己 userId 创建的。
2. **提示词分布**：品牌 ~5%（3 条 baseline）/ 品类 ~65% / 竞品 ~30%（无竞品时退化为品类题）。所有提示词固定中文。
3. **并发限流**：按引擎分组信号量，默认每引擎并发 3，避免触发对方限流。引擎来源由 `LlmModel` 表动态决定（不再硬编码）。
4. **状态机**：`processing → complete / failed`。execute 立即返回 `{ dispatched: true }`，实际执行异步进行；前端轮询 `/status` 拿 `promptDone/promptTotal` 进度。
5. **评分**：0-100 分 + A+/A/B/C/D/F 等级；产出 `result` JSON 快照（含各引擎细分、盲点、综合建议）。
6. **Skill 打包**：详情页可下载诊断 Skill ZIP，内含本次诊断的提示词 / 结果 / 元信息，便于离线复用。
7. **重新诊断（rerun）**：复用原诊断的 brand/website/industry/description/competitors/keywords/features/tier 配置，生成新 jobId 的新任务并自动调用 execute；原报告保留不变。前端在 `complete / failed` 状态显示「重新诊断」按钮，二次确认后调用，成功后跳转新 jobId 详情。
8. **apiKey 解密**：`LlmModel.apiKey` 为 AES-256-GCM 加密存储（详见 `llm-model.service.impl.ts`）；`engine-client.ts` 的 `loadEnabledEngines` 读取时必须用 `decryptApiKey` 解密，同时通过 `isEncrypted` 兼容历史明文数据。
9. **聚合不可过滤 error 结果**：`runAuditJob` 拉取 prompt 结果时只能过滤 `p.result` 为空的，**严禁过滤 `p.result.error`**。带 error 的 prompt（如引擎 401）必须参与聚合 —— aggregator 对空 text 返回 `genuine=false`，从而正确归入盲点。否则会出现「提示词分析里满是盲点、但盲点页签显示 0 个」的严重错误。

## 2026-07-01 发布后自动检测闭环

### 功能说明

- 发布链接写入 `published_article_links` 后，由后端 `citation-detection.scheduler.ts` 定时扫描并自动发起 AI 引用检测。
- 自动检测复用现有引用诊断采集、URL 标准化匹配、台账写入与永久模型命中标签逻辑。
- 发布同步流程不等待检测结果，自动检测失败不影响发布订单同步或发布链接入库。

### 业务规则

- 默认每 30 分钟触发一次，可通过 `CRON_CITATION_DETECTION_INTERVAL` 配置。
- 每轮最多处理 5 条待检测发布链接。
- 每条发布链接最多使用 2 个问题，模型范围为系统 LLM 配置中全部启用、未删除且 API Key / baseUrl / modelName 完整的模型。
- 24 小时内同一 `articleLink` 已有 detection run 时不重复自动检测。
- 单条链接失败只记录日志并继续处理下一条。
- 平台缺少模型配置或 API Key 返回 `skipped`，不计为系统失败。
- 调度器日志不得打印 API Key。

### 验收标准

- `npm.cmd run lint` 通过。
- `npx.cmd tsc -p tsconfig.api.json --noEmit` 通过。
- 调度器启动后按 cron 异步扫描 `published_article_links`，不阻塞发布流程。

### 功能说明

- 自动引用检测默认读取 `llm_models` 中全部启用且配置完整的模型，不再硬编码 `DeepSeek/Kimi`。

- 成功响应继续保存真实回答，并从响应体和回答文本中解析 URL 来源；没有 URL 时不写 citation record。
